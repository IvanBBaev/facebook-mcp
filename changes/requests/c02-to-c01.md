# Request: C02 → C01 — truncation-safe paging in the result shaper

**File:** `src/mcp/result.ts` (owned by C01).

**Change.** When the shaper's budget levers drop items from a list in a result
that carries `nextCursor`, the result must not keep a cursor that resumes past
the dropped items:

1. Drop items from the **end** of the array only (largest prefix that fits, as
   lever 1 already does for arrays), never from the middle.
2. If any list item was dropped and the result has a top-level `nextCursor`,
   **remove `nextCursor`** and set `truncated: true`.
3. Report the event in `notes[]` (C02 contract, `src/tools/shared/list.ts`,
   `notesFields`) as well as in `_truncation`: how many items were kept, and
   that the caller should re-request the same page (same `after`) with
   `limit` equal to the kept count to continue without a gap.
4. Optional, if C01 prefers resuming in place: accept a per-result
   `resumeCursor` (the `after` that produced the page) from the tool and emit
   it as `nextCursor` together with a `skip` count. Not required for 1.0.

**Reason.** AUX-02 (`docs/reviews/v3/06-mcp-agent-ux-engineer.md`): a 100-item
`list_comments` page returns ~50 items, and `nextCursor` still points past the
50 dropped ones, so an agent that follows the cursor silently loses them. Graph
returns one `after` cursor per page, not per item, so the cursor cannot be moved
to the last kept item from the api layer; the shaper is the only place that
knows what was dropped. C02 (wave 1) ships the list contract and helpers; the
lane tasks (L2.reader, L2.moderation, L2.messages) adopt the list-level taint
envelope, which removes most of the per-item overhead, but the cursor rule still
has to hold whenever the budget is hit.

**Acceptance.** A shaped list result never has both dropped list items and a
`nextCursor`; a test drives a page over budget and asserts `nextCursor` is
absent, `truncated` is true and `notes` names the kept count.
